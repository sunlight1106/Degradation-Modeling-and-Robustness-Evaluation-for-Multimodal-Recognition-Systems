# 把平台开放给其他人

## 先理解：数据保存在哪里

所有访问者必须打开**同一个网站地址**。注册账号、保存笔记、添加联系人和发送消息，都会写入该网站的服务器数据库；换电脑登录同一地址，便能读取自己的数据。

- 目前的 `http://localhost:4273` 指向你自己的电脑，还不是云端。
- 把这套服务部署到云服务器后，保存成功就是保存到了云端，无需每条笔记再点“上传”。
- GitHub 只存程序和文档，**不会上传用户数据库、聊天记录、笔记、附件或密钥**。
- 别人各自下载仓库、各自启动，会得到互不相通的独立平台。当前不提供跨站账号互通或自动合并两个数据库。
- 云端存储不等于公开可见：笔记默认私密，只有主动分享的链接才开放对应内容。父页面分享不自动开放子页面。

## 用户怎么使用

1. 打开你部署好的 `https://你的域名`，点击「注册」，再登录。邮箱目前用作账户资料，未接入邮件验证与邮箱找回；不要把填写邮箱视作已验证身份。
2. 进入「我的笔记」→ 新建笔记。填写标题和正文，停止输入约 1.5 秒后自动保存；看到「已保存到服务器」再关闭页面。
3. 网络失败时，页面保留草稿并提示重试。当前账号的未同步修改会保存为浏览器草稿，重新联网打开后可恢复；浏览器空间不足时请点「下载当前草稿」。完整离线打开尚不支持。连接恢复后会再次尝试保存。
4. 同一笔记在另一个设备更新后，旧页面会显示冲突。先下载当前草稿，再重新加载服务器版本并整理合并，避免覆盖新内容。旧 API 客户端不传 `baseRevision` 的手动保存仍兼容；新的网页编辑器始终传版本号。
5. 进入「联系人与聊天」，输入完整身份码，或至少 2 个字符的用户名、昵称前缀，点击「查找用户」→「申请添加」。每次最多展示 20 人。
6. 对方在「申请」中同意后，双方可以私聊；发送附件可点「发附件」，进入既有站内信。多人讨论、成员权限和资料共享使用「群组协作」。
7. 关闭「允许其他用户搜索到我」可停止被搜索；已有联系人和待处理申请不受影响。搜索不显示邮箱、笔记或其他私人资料。
8. 删除联系人会停止私聊。屏蔽还会拦截双方站内信；共同群组的权限独立管理，需要在群组中退出或移除成员。拉黑保留已同意的联系人关系，双方都解除限制后可恢复交流；已删除的联系人或未同意的申请不会自动恢复，关系变更后 24 小时可重新申请。清空聊天记录只隐藏本人账户的历史，跨设备生效，不删除对方的记录。私人备注、置顶、免打扰及阅读位置按当前用户独立保存。

联系人与待处理申请合计每人最多 200；新申请每分钟 10 次，聊天发送每分钟 60 次，另有通用请求限流。聊天页可见时约每 5 秒检查新消息，隐藏时暂停，下次打开能读取历史。目前没有语音、视频通话、后台系统通知、已读回执或端到端加密。私聊接口不向无关用户或管理员开放，但服务部署者仍能通过运维数据库读取数据。

## 准备云服务器

下面是**单台 Linux 服务器**的部署方案。需要 Docker Engine 与 Compose v2、Git、一个域名，以及指向该服务器公网 IP 的 DNS A 记录；有 AAAA 记录时 IPv6 也必须能正确访问。

开放网站所需的 **80/TCP、443/TCP**（443/UDP 可选，用于 HTTP/3），SSH 仅允许你的管理来源。数据库、Redis、MinIO、后台 API 不需要公网端口。不要开放整个 Docker 内网。服务器需容纳 MySQL、Java、扫描器、对象存储和镜像构建，可从 4 核 / 8 GB 内存及足够的数据磁盘开始，再按实际使用量调整；这不是容量保证。

### 1. 下载并初始化

在云服务器终端执行：

```sh
git clone https://github.com/sunlight1106/Personal-Knowledge-Base-and-AI-Recognition-Evaluation.git
cd Personal-Knowledge-Base-and-AI-Recognition-Evaluation
sh deploy.sh
```

第一次会创建私密 `.env`，自动生成管理员密码和服务密钥，并启动仅服务器本机可访问的版本。私下打开 `.env` 查看 `BOOTSTRAP_ADMIN_USERNAME` 和 `BOOTSTRAP_ADMIN_PASSWORD`，不要贴进聊天、截图或 GitHub。

### 2. 配置域名

在 `.env` 添加一行，换成真实域名，不带 `https://` 或路径：

```dotenv
SITE_DOMAIN=study.example.com
```

检查域名 DNS 已指向服务器。公网模式使用 `172.30.73.0/24` Docker 网络；如果与服务器其他网络冲突，先统一调整 `compose.public.yaml` 的网段、固定地址，以及 `scripts/public/nginx.conf` 的信任地址。不要只修改其中一个。

### 3. 开放 HTTPS 网站

```sh
sh scripts/public/deploy.sh
```

脚本校验配置后重新创建容器和网络，保留命名数据卷；切换期间有短暂停机。新增 Caddy 网关负责 HTTPS，数据库仍只在内部网络中。不要同时运行其他占用 80/443 的服务。域名解析正确、端口可达时，Caddy 会申请并续期证书，见 [Caddy 官方说明](https://caddyserver.com/docs/automatic-https)。网关启动不代表证书一定签发成功，首次部署需从外网实际验证。

```sh
docker compose -f compose.yaml -f compose.public.yaml ps
docker compose -f compose.yaml -f compose.public.yaml logs --tail=80 gateway
```

从另一台设备的浏览器打开 `https://你的域名`。用两个测试账号完成注册、搜索、申请、同意、聊天，再用同一账号在两个浏览器打开一篇笔记，确认自动保存和冲突提示。向公众开放前，自行补齐适合运营范围的用户支持、内容管理、注册滥用防护与邮件验证；本方案是小规模平台基础，不代表完成大型社交服务的运维体系。

## 后续更新与数据保护

之后一直使用**相同目录与两个 Compose 文件**，避免混用私域启动命令：

```sh
git pull --ff-only
docker compose -f compose.yaml -f compose.public.yaml up -d --build --wait --wait-timeout 600
docker compose -f compose.yaml -f compose.public.yaml exec -T frontend nginx -s reload
```

不需要再次执行切换脚本；迁移会在后端启动时自动运行。不要使用 `down -v`：它会删除数据卷。

定期备份至少包含 **MySQL 数据、MinIO 对象、原 `.env`/主密钥**，并放在独立且加密的存储上。网关证书存储也应持久化。首次把电脑数据搬到云服务器，需要单独安排停写迁移与恢复验证；复制代码不会复制这些数据。默认 Compose 部署可使用 [加密完整备份工具](COMPOSE_BACKUP.md)。仓库原有的 [本地恢复演练工具](../scripts/backup/README.md) 只覆盖其明确支持的 MySQL + 文件系统开发环境，**不能备份默认 Compose 的 MinIO 数据**。目前未配置任何自动异地云备份；请使用云厂商的备份能力或经过恢复演练的数据库/对象存储备份方案。

默认前端端口仍只绑定服务器 `127.0.0.1`，外网经 HTTPS 网关进入。公网配置只信任网关到前端、前端到后端的固定地址来识别访客来源，不能通过伪造请求头绕过登录限流。

常见问题：

| 现象 | 检查 |
| --- | --- |
| 外网打不开 | DNS、云安全组、防火墙和 80/443 是否被其他服务占用 |
| HTTPS 证书失败 | 网关日志、错误 AAAA 记录、DNS 是否完成解析、ACME 服务是否可达 |
| 登录跨域报错 | `.env` 中域名是否正确；使用两个 Compose 文件重新启动后端；不要混用 IP 与域名 |
| 找不到其他人的账号 | 是否在同一个网站注册、搜索是否匹配前缀、对方是否关闭搜索或屏蔽 |
| 保存失败 | 保留当前页面，下载草稿；检查网络、登录状态和版本冲突提示 |
| 更新后短暂 502 | 等后端健康，再执行上述 Nginx 重新加载命令 |
