# DEMO 队列故障恢复与并发边界

本页只适用于旧 DEMO 实验 (`/api/v1/inference/tasks`)。个人 BYOK 文本/图片调用是另一条逐次确认的同步路径，不会进入此队列，也没有自动重发或付费调用恢复功能。

## 已修复的问题

- 文件增强等参与事务的服务抛出异常时，先让执行事务完整回滚，再以独立的新事务写入 `FAILED`、错误说明和完成时间。不会在仍持有旧事务锁时启动失败写入。
- 同一个任务 ID 的并发交付，在检查 `PENDING` 前取得数据库悲观行锁，持锁直到执行与平台用量账本一起提交。成功后的重复交付直接返回，不再次生成结果或写一笔用量。
- 失败写入也重新取得同一行锁，并只更新仍为 `PENDING` 的任务。如果另一个交付已经完成，旧失败不会覆盖其结果。
- 初次入队和恢复入队遇到 Redis 超时，都不会把已保存的任务直接判成失败。Redis 可能已经接收了写入。初次请求返回错误时，应去 Logs 刷新状态，避免创建另一个新任务。

这些改动不代表跨数据库、Redis、对象存储的“恰好一次”执行。

## 本人手动恢复

进入 **Logs**，先点 **刷新状态**，展开本人长期处于等待中的实验，点击 **重新入队 DEMO 实验** 并确认。

- 恢复使用原任务 ID、原输入、原模型和原 `trace_id`，不创建新任务。
- 仅允许具有 `experiment:run` 权限的任务本人，且输入文件也必须属于本人。管理员没有代别人恢复的特权。
- 服务端只接受 `PENDING`；`COMPLETED`、`FAILED`、已持久化的 `RUNNING` 均返回 `409 TASK_NOT_PENDING`。状态可能刚被 Worker 更新，应先刷新。
- 请求为 `POST /api/v1/inference/tasks/{id}/recover`，返回现有 `InferenceView`。响应新增 `requestedById`，让页面依据身份 ID 显示本人按钮，不能用显示名作为归属判断。
- 该 POST 与新建实验共享 inference 每分钟频率限制（默认 20 次）。GET 刷新不消耗该执行预算。
- 页面取消确认不会发送 POST；等待响应时阻止重复点击，离开页面或换账号后忽略旧响应。
- `PENDING` 响应只表示重新入队请求已被接受，不表示 Worker 已执行。页面明确提示再次刷新查看最终结果。
- 网络失败、Redis 超时后原记录保留。可以刷新后再对同一条等待记录恢复，不要复制创建新实验。
- Inline 开发模式中，恢复在检查事务提交后同步执行同一个任务，仍受相同锁和 DEMO 限制。

## 明确的限制

Redis 仍使用 `RPOP`。创建任务提交与入队之间，或弹出与处理之间发生进程崩溃，可能留下 `PENDING`；此次提供的是本人手动恢复，不是持久化消息确认/outbox，也不是自动扫描重试。

执行事务中的 `RUNNING` 尚未提交，所以其他页面在 Worker 运行期间仍可能看到 `PENDING`。恢复请求取得同一任务行锁，可能等待已有执行（尤其视频预处理）结束；若它已完成，请求返回状态冲突，而不会重跑成功任务。此长事务仅适用于现有本地合成 DEMO 流程，不能复用于真实供应商网络调用。

执行失败回滚后，到 `FAILED` 标记取得行锁之间，另一个等待中的交付可能先执行。失败的合成尝试因此可能重复；最终成功最多提交一份结果和一笔该任务用量。数据库事务不能回滚已经写入的对象字节，进程中断可能留下未引用的派生对象。此次不自动删除文件或扫描、修改旧数据。

若数据库本身不可用，失败状态也可能无法保存，任务仍可能为 `PENDING`。恢复数据库与 Worker 服务后，由本人刷新并决定恢复。旧的 `FAILED` 和异常持久化 `RUNNING` 记录不会自动重置。

## 自动回归与验证

`InferenceRecoveryIntegrationTest` 默认在 H2 上运行；设置 `MYSQL_TEST_URL` 后在真实 MySQL 上创建并仅删除自己的随机临时数据库，执行同样的 11 项测试。存储、媒体、杀毒、模型均使用合成测试替身，没有读取真实用户文件、Redis 队列或调用供应商。

覆盖范围：

- 真实事务代理的 `FileService` 增强失败，回滚后持久化 `FAILED`，Worker 继续处理下一条。
- 六线程重复交付：一次合成调用、一次真实 BillingService 用量提交、零元 DEMO 费用。
- BillingService 已写账本后故障：整笔用量事务回滚，再保存失败。
- 六线程失败：最终失败信息可见且无用量账本；不假设失败尝试只执行一次。
- 回滚后另一个交付先成功：旧失败标记不能覆盖成功数据。
- 终态/未知 ID 不执行；模拟 RPOP 后中断，再恢复同一 ID。
- HTTP 未登录、无执行权限、其他用户、管理员、借用别人文件、终态、未知任务与 DEMO 模式限制。
- 初次入队超时及“Worker 已完成后客户端才收到入队错误”的交错，不破坏原记录。
- 恢复入队超时不把等待任务改为失败。

`RateLimitFilterTest` 覆盖恢复和创建共享执行预算；`queue-recovery-ui.mjs` 覆盖确认取消、重复点击、权限按钮、状态刷新、错误信息及换账号/卸载后的迟到响应。

本地验证命令：

```sh

npm run test:ui --prefix cle
npm run build --prefix cle
# 仅连接一个可创建和删除临时数据库的隔离测试实例，勿指向生产库：
MYSQL_TEST_URL='jdbc:mysql://127.0.0.1:3306/?allowPublicKeyRetrieval=true&useSSL=false&serverTimezone=UTC' \
MYSQL_TEST_USERNAME=root MYSQL_TEST_PASSWORD='isolated-test-password' \
./mvnw -B -Dtest=InferenceRecoveryIntegrationTest test
```

## 次日验收

在隔离的 DEMO 环境与合成图片上：

1. 保留 Redis/API 服务，暂时停止 Worker，创建一条 DEMO 实验，确认 Logs 中等待状态可见。
2. 在 Logs 展开本人任务，取消恢复确认，确认状态无变化；再确认恢复，同一 ID/trace 保持不变。
3. 启动 Worker，刷新后确认只保留一个完成记录、账本只有一条该任务的零元用量。此步队列含重复 ID，验证终态不再执行。
4. 换另一个用户及管理员查看，不应允许恢复别人任务；已完成/失败任务也不可恢复。
5. 如果 Worker 崩溃导致丢失交付，恢复后由本人重新入队等待记录。不要用停止进程或损坏存储的方式测试真实用户任务。

命令测试验证事务与页面逻辑，不等同于生产部署、原生浏览器外观验收或真实 Redis 崩溃/对象存储全栈验收。
